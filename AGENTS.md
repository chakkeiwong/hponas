# HPO-NAS execution guidance

The master is `CONSOLIDATED_MASTER_AUTHORITY.md`; `docs/program/program.json` owns dependencies, current work and evidence. The banking product scope is `docs/program/BANK_HPO_NAS_PRODUCT_CONTRACT.md`. Preserve the accepted finite baseline, immutable evidence, original lineage and explicit unsupported outcomes. Read the active stage before changing scientific code.

Use one inspector/editor at a time. At phase boundaries, repair demonstrated defects, refresh the next bounded plan and continue authorized work. When describing a next action, name its master stage and explain any scope change or blocker. Mutation qualification is one gate, not completion of the product.

For routine operations use the exact absolute commands in `docs/PROGRAM_OPERATIONS.md`, with no environment prefix, interpreter wrapper, added flags or command chaining. The runner owns its environment, fixed roster, timeouts and logs. Add relevant new tests to the reviewed roster when a feature changes. These commands do not allocate scientific campaigns or qualify changed source automatically.

Prepare necessary new operation classes as concrete bounded manifests, review them, and group any required managed approvals. Do not repeatedly request permission for authorized reversible work. Dedicated allow rules do not override managed approvals, protected paths or a rejection. Do not broaden global Python/bash/network rules.

Sibling repositories supply read-only contract context. Keep the package, stylized examples and their known-answer references independent of sibling imports, data, runtime environments and services. Separate-machine testing remains waived. Do not send external messages, run a broad campaign, mutate git history or deploy merely because a local verification command is allowed.
